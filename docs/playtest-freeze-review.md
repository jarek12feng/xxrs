用户随后要求按成长优先级实施必要优化，并明确“A版本试玩包无需保留”。当前开发不再受下述历史冻结限制；本轮范围、验证与剩余问题见 [成长体验迭代](growth-iteration.md)。A 版记录保留为历史证据，不代表当前代码的验证结果。

## 原冻结决定

按用户要求冻结当前体验，暂停新增功能、系统、剧情内容及数值调整，先做前 30 分钟陌生玩家观察。状态为“Demo 试玩候选”，不等于正式发行、收费或商业验证通过。

冻结编号：`playtest-20261029-A`。应用版本仍为 v0.14.0，存档格式为 v14。基准提交 `6a60168` 加当前本地未提交修改；仅用提交号或 package.json 版本号不能唯一标识本轮。具体文件指纹见 [冻结清单](playtest-freeze-manifest.md)。冻结是协作约束与可核对基线，不是 Git tag、已提交版本或文件系统写锁。

## 复评结论与证据边界

| 方向 | 本轮改善 | 尚不能得出的结论 |
| --- | --- | --- |
| 成长爽感 | 装配、研修和精炼显示真实收益差异；照夜篇、灵器继续影响后续关卡；药品用途更明确 | 玩家已经理解或愿意为成长体验付费 |
| 构筑差异 | 擂台允许六回合，长春耗草续航、剑经承担承伤、归元辨阵；存在不同成本的可胜策略 | 所有种子、辅修、装备组合均已平衡 |
| 前 30 分钟 | 已完成目标不再反复提示；主线与寻亲支线区分；失败后有恢复路线 | 冻结版本首次游玩节奏、独立完成率或继续游玩率达标 |
| 工程与性能 | 独立成长投影、复用战斗预览；迁移保护与规则回归通过 | 浏览器端保存到可见反馈及低配设备性能已通过 |

本次复评已重新运行：34 个测试文件、306 项测试全部通过，`npm run build`、`git diff --check` 通过。复评基于源码差异、规则测试与其他 session 的执行记录，没有重新完整人工通关。执行记录中的 94% → 100% 等界面案例属于此前开发回归，不是本次独立盲测数据。

现有战斗矩阵使用固定种子 42、固定辅修和装备搭配。普通准备决胜场的剑经与归元示例同为三合、同一动作序列，归元剩余气势更多；长春可用更多灵草换生存，零草时该场不能胜。这说明需要进一步检验优势是否清晰，不能推断归元全面更强或长春设计失败。

## 剩余问题与验证优先级

以下优先级指观察顺序，不授权在冻结期间调参。

| 编号 | 优先级 | 问题或假设 | 验证方式 / 关闭条件 |
| --- | --- | --- | --- |
| R01 | P0 | 首次成长是否来得及时、奖励是否被漏装 | 记录首次获取/装配/使用时间；按原计划装配与成长门槛评估 |
| R02 | P0 | 古阵后筑基准备是否出现长时间重复劳动 | 记录进入准备段时间、最长无有效选择段与主动退出原因；若 30 分钟未到达，标记未覆盖，不跳关凑数据 |
| R03 | P0 | 无指导能否知道下一步，失败后能否恢复 | 记录导航停滞、求助和恢复动作；辅助完成不算独立通过 |
| R04 | P1 | 构筑是否改变玩家决策，而非只换名称 | 首玩后另做等预算对比，记录选择理由；补多种子与更多辅修/装备场景，查单一优势策略 |
| R05 | P1 | 清心丹降价且收益提高，是否过早封顶神识 | 记录首次服药、神识封顶时刻、材料机会成本及封顶后的目标；当前仅为待验证风险 |
| R06 | P1 | 擂台同归判负与青嶂击倒后不反击的差异是否可预期 | 不先解释规则，观察选择前预期与结算后理解；首玩未遇到则单独补测并标明来源 |
| R07 | P1 | 浏览器保存/渲染是否拖慢反馈，是否累积后台资源 | 生产构建测量命令到可见反馈 p95，长档及 50 次切换；按计划性能门槛记录结果 |
| R08 | P2 | 正式目标平台发行可靠性仍缺证据 | Windows 实机安装、更新、退出重进、坏档恢复等独立验收；不阻止受控网页版观察 |

## 冻结规则与退出条件

- 允许只读评估、运行测试、填写观察表、更新文档及使用隔离测试存档。不得修改玩家真实存档或在试玩中注入资源、跳关。
- 暂停功能扩展、奖励/成本/概率/回合数调整、体验文案与布局改动，以及与本轮无关的重构。依赖升级和构建配置变化同样会改变基线，不能悄悄混入。
- 试玩使用固定生产构建，不使用会随其他 session 热更新的开发服务。测试前核对指纹；为所用产物记录独立路径/地址及校验值。用户随后授权打包供邀请试玩，产物及验证范围见 [Windows 交付记录](playtest-windows-package.md)；打包不解除功能与数值冻结。
- 发现崩溃、存档损坏、无法继续等阻断问题时暂停受影响样本，保留数据与复现步骤。修复应作为明确的维护任务处理，并重新验证、生成新的冻结编号；不得直接替换 A 版后仍沿用 A 版统计。
- 其他 session 若改了代码，指纹检查会发现漂移；先保留变更并确认测试来源，不回滚别人的工作，不把新版本数据并入旧样本。
- 完成 5–8 名新玩家首轮观察后汇总 R01–R06，提出最少必要修改。由用户决定解冻和下一轮范围；时间经过、测试通过或口头好评不自动解冻。
- 5–8 人仅用于发现问题；原计划的比例门槛在后续 20–30 人样本验证。未发生的场景标记未覆盖，不能记为通过。
