# 二维场景与修行时间统一约束

2026-11-03 新增 [世界地图、距离与旅行设计](world-travel-design.md)。跨地区按路线总距离与方式结算，近郊不逐次切图收费；御剑学习与首批六地进度见 [实施记录](wayfaring-review/README.md)。

日期：2026-11-03。依据用户确认：按 TypeScript + Phaser 二维场景方向重构；场景切换不能只换文字；时间尺度须随境界提升变化。本文为后续场景、旅行、修行、剧情日程和存档开发的共同约束。与旧的按画面切换计时、统一闭关跨度等提案冲突时，以本文为准。

## 产品目标与实施边界

目标仍为本地单机、Windows 桌面与 Steam 发行。第一批以渡口—药庐—雾林—山祠—领取功法为可玩切片，不据此宣布全游戏二维化。先验证空间、互动和现场反馈，再逐段推广；不同时重写全部境界，不把二维化自动扩大为即时动作战斗或开放世界。

保留纯 TypeScript 规则核心。Phaser 管理场景、镜头、角色表现和局部效果；Vue 管理语义化交互、背包、功法和设置。两者都只能发出领域命令，不得直接修改资源、剧情、种子或存档。技术选择不代表已经通过 Steam 或 Windows 实机验收。

## 一、场景必须能行动

每处主要场景须回答：玩家在哪里、可接近或调查什么、可以从哪里进入和离开、行动后现场怎样变化。

- 操作与场景对象关联：人物交谈、药炉准备、痕迹辨路、阵门应对，不把所有行为重新堆成无空间关系的全局按钮列表。
- 可交互对象必须能发现，并有鼠标、触摸和键盘可操作入口。不要靠像素狩猎或颜色辨认必要机关。
- 角色走近与短转场提供空间反馈，不收取规则资源；附近操作不强制长距离走动，反复经过的已知路线不以等待拖时长。
- 场景内观察只读状态，不暗中授予经历、能力、奖励或任务资格。若观察会影响后续规则，须进入领域命令和存档。
- 准备、胜利、修复、取走物品等变化从成功持久化的状态派生。保存失败不得提前开门、发奖、播放成功或切换到下一剧情地点。
- 不为增加互动把一次行动拆成无选择、无新信息的多次确认。关键过程应至少提供观察、应对或现场变化之一。
- 保留已知剧情事实，不把守祠妖修替换为人族敌人或傀儡，不虚构同伴在场、受伤和资源。
- 减少动态效果时保留所有信息和可操作性；渲染失败要有可继续的文字操作入口。场景卸载清理引擎、监听器和动画；后台暂停表现循环。

## 二、现实操作时间与世界时间分离

现实操作时间是移动、演出、读文和操作所花的秒数；世界时间是角色年龄、寿元、约定所使用的月/年。两者不得按比例自动换算。

- 不因现实离线、挂机看画面、阅读、暂停或开菜单扣除寿元。
- 二维角色走几步或跨一个画面不自动推进月份。
- 世界时间只能由规则命令结算，不能由动画结束、帧数、浏览器计时器或加载速度推进。
- 现实首次筑基 60–90 分钟仍为真人体验目标，不是强制等待或计时解锁条件。

## 三、按境界改变操作尺度，底层统一按月

当前底层继续以整数月记账，年龄和寿元沿用同一时间单位；一年为十二个月。不要同时建立一套年计时和一套月计时，也不要为二维场景引入小时级日历。

| 行为 | 炼气 | 筑基 | 金丹及后续已授权境界 |
| --- | --- | --- | --- |
| 常规修炼 | 月为主要选择单位 | 数月到数年，保留短修 | 年为主要展示尺度，保留短修与提前出关 |
| 长关 | 依据阶段、瓶颈和余寿提供选项 | 按阶段提供更长跨度 | 按当前已开放进度提供，不因年单位放开未来境界 |
| 场景内交谈、观察、走动 | 不推进年月 | 不推进年月 | 不推进年月 |
| 旅行 | 依据距离、路线与通行能力 | 同一路程可因能力节约时间 | 不因境界高而把所有移动统一改成多年 |

上述是尺度要求，不是新的具体收益和月份常量。每个具体闭关跨度、路线成本须在对应领域配置中明确，提供现值、新值、资源/寿元影响和回归证据后实施。不要凭本文批量改变现有数值。

显示采用清楚的年/月组合，例如十八个月显示“一年六个月”，不能四舍五入隐藏成本。出发或闭关前展示耗时、预计结束年龄及余寿。对于到目标或事件暂停的可变时长，须明确“最多”与停止条件。

## 四、旅行按距离与用途分层

| 层级 | 规则 |
| --- | --- |
| 室内、同一局部场景 | 不计年月；如药炉到门口、接近 NPC |
| 开场短途寻人 | 渡口—药庐—雾林—山祠属于同一次短途，不新增月份成本；准备失败与回撤不以重复切图收费 |
| 普通地区往返 | 由路线统一定义成本；禁止每次切换背景默认扣一个月。尚未定义的路线不得由 UI 擅自补成本 |
| 长途探险、出海、跨域 | 出发前展示真实路程成本及可预知风险；由命令推进，沿用领域中断规则 |
| 熟悉路线快速旅行 | 可省现实移动操作，不默认免除世界时间成本；具体路线开放须有到访/通行依据 |
| 战败、撤退与恢复 | 明示伤势、物资和恢复耗时；区分撤离成本与整备成本，不重复结算同一段路程 |

高境界的能力应可以缩短同一路线的旅行时间或开放此前无法抵达的路，但必须有真实规则，不只写“御剑更快”。未实现的御剑/传送不能作为已生效折扣。

## 五、闭关、约定与中断

- 选择跨度随境界和阶段改变，短修、常规和长关都必须有明确用途。
- 优先支持修至当前目标、瓶颈或指定上限即出关，不强迫吃满所有选定月份。
- 按月推进结算，保持资源、寿尽、事件优先级一致，不能按年一次加收益后补判死亡。
- 已知的重要约定在长关/远行前提示。跨过该约定须让玩家明确选择赴约、缩短行程或承担已说明的失约后果。
- 遇到必须处理的剧情应暂停；暂停后的已花时间、实际所得、未扣物资和下一步必须准确说明，禁止重复发奖。
- 不按现实倒计时惩罚离线，也不能暗中用一次长关使重要人物死亡或关系清零。
- 尚未开放的大会、境界和任务只作明确预告，不扣资格、不吞奖励、不伪造完成。

具体暂停点及可主动错过的约定须在对应领域规则定义，不能由表现层笼统拦截所有故事。

## 六、成长与奖励的呈现

首册功法应在领取处提供明确的装配选择，避免获得之后还要在未习得列表中寻找。已有主修时不得静默覆盖；功法页优先展示当前装配与已拥有内容。

试招和演示必须标明是否为练习。只读演示不得发真实奖励、扣真实灵草或留下伤势；正式战斗必须走真实规则。新能力应在后续关卡实际用上，而不是只出现一次动画。

关键节点只突出当前一项决定；重复目标、旧回执和长背景折叠。不得删去不可逆后果和资源成本来换取简洁。

## 七、验证与交付

每一批场景改造须记录：

1. 新角色可通过正常 UI 完成哪些地点、选择和结果；哪些仍是旧表现。
2. 走动、观察不改变年月/种子/资源；领域命令固定种子可重放。
3. 保存失败、加载失败、退出/重进、读档恢复、连续点击及事件锁定不会误推进。
4. PC 分辨率、窗口缩放、鼠标与键盘、减少动态效果与后台/卸载资源释放的验证范围；窄屏适配单独作为次级检查。
5. 规则变化的自动测试、构建与 diff 检查；浏览器开发检查与陌生玩家、Windows 实机、Steam 发布分别报告。

本文件是统一约束，不是验收结果。首批实现与测试记录另见 scene2d-review.md；没有证据的项目不得标记完成。

## 8. 身处世界的体验要求（2026-11-03 最新确认）

用户明确要求：玩家的视野是进入修真世界，在世界内交流、操作。探索页不得再采用“上方长文、中间插图、下方按钮”的文章布局；折叠文字只是基础整理，不等于沉浸体验完成。

- 探索主画面占据视口；人物、器物、道路承担交互入口。HUD 与随身功能退到边缘，不上下滚动寻找场景操作。
- 常态只展示地点、简短眼前目标与可发现对象。点击或键盘选中对象后才出现针对它的观察和动作；关闭后恢复现场。不得把所有系统说明常驻在场景上。
- 对话发生在人物所在现场，人物应有朝向、回应与动作反馈；长经历进入可打开的见闻。不能用持续大段文字冒充人物演出。
- 配药应看见药炉与操作反馈，破阵应看见阵势变化，救人应看见被救者脱险。以存档成功后的结果驱动表现；动画不另算成功，不篡改规则。静态姿态平移、提示牌更名不视作完整行动演出。
- 旅行由场内出口衔接地点，进出方向和角色位置应有连续性；不可为每次短距离行动强制播放冗长过场。局部行动仍不扣修行年月。
- 按钮使用明确动作；关键消耗、风险、不可逆后果在行动前可见，不能藏在悬停提示里。说明支持点击、键盘展开，不能仅靠 hover。
- 功法、储物袋等管理功能作为可关闭的界面打开，不能要求玩家为了继续交流来回穿梭多个管理页。战斗单独组织敌我、动作和即时反馈，不套探索文章模板。
- 以 PC / Steam 体验为首要验收目标；具体优先级见下节。截图、可玩操作、规则回归分别记录；“布局通过”不能写成“沉浸感已验收”。

### 推进顺序及完成边界

先验证渡口→药庐→雾林→山祠的一段完整连续体验，再推广后续区域。当前全视野布局与场内对象操作是第一步；场景角色行走/交谈、药炉准备演出、被困者营救演出仍需后续制作与接入，不能以四张背景图代替验收。每个场景需要同时交付场内入口、行动反馈、世界结果和操作可达性，而不是先批量增加地图数量。

## 9. PC / Steam 优先（2026-11-03 用户确认）

- 桌面版为主设计，先把 PC 的场景构图、人物比例、现场互动和文字可读性做好；窄屏是次级兼容，不为适配手机压缩人物、拆散操作或改变桌面构图，不作为当前重构的主要验收依据。
- 以 1920×1080、16:9 为设计基准；检查 1280×720、2560×1440、窗口缩放及系统显示缩放后的可读性和遮挡。以上是待执行的验收目标，不代表已完成测试。
- 鼠标点击人物、器物和道路作为主要现场入口，键盘提供功能快捷键、可见焦点与退出操作。悬停可提供补充说明，关键消耗和不可逆后果仍须在行动前直接可见。
- 背包、功法等管理界面利用桌面宽度组织列表和详情；探索保持场景主导，避免纵向长页和寻找屏幕外按钮。
- 全屏与窗口模式、Windows 实机表现属于发行前检查；手柄和 Steam Deck 另列后续范围，不能因目标为 Steam 就宣称已支持。当前不以手机或触屏交互为主导。
